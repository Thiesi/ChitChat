# ChitChat v3.10.0

`v3.10.0` makes live updates reliable: a message that is saved a moment late is never skipped, and open tabs recover by themselves after an upgrade. It finishes room ownership transfer in the web client, redesigns the stewardship pages and the rest of You, and reports phone-alert and backup health in the System status API and `/metrics.php`. Message search can be limited to one room (API). The System status card, the two new Operational settings fields and the web search room filter follow in a later release. API v1 changes are additive. It adds two forward-only database migrations (`0059` and `0060`) and needs no configuration changes, so back up before upgrading. Nobody is signed out.

## Project status: feature-complete

This release does not change [project status](../README.md#project-status-feature-complete). It continues the maintainer-approved presentation overhaul and adds maintainer-approved reliability and operability work, all tracked in [#163](https://github.com/Thiesi/ChitChat/issues/163). See [`docs/roadmap.md`](../roadmap.md).

## Added

- **Room owners and staff can hand a room on in the web client.** ([#300](https://github.com/Thiesi/ChitChat/issues/300); [#303](https://github.com/Thiesi/ChitChat/pull/303), [#306](https://github.com/Thiesi/ChitChat/pull/306), [#307](https://github.com/Thiesi/ChitChat/pull/307))
  - "Make owner of #room…" is on a member's profile card. Staff get "Make owner…" and "Take ownership…" under Administration → Rooms.
  - Each asks for a fresh privileged confirmation first. The new owner sees it in Activity, and so does the previous owner unless they made the change themselves or their account is closing or closed.
  - The options appear only when the server's transfer rule allows it. A ban is taken into account only for viewers who can already see bans (Administrators and up), so a room owner or Chat Admin may be offered a banned member; the transfer then says that person can't own the room right now. A refusal because the situation changed meanwhile is explained too.
- **Phone-alert and backup health, in the API and metrics.** ([#310](https://github.com/Thiesi/ChitChat/issues/310), [#313](https://github.com/Thiesi/ChitChat/pull/313))
  - Push: queued, due and failed deliveries, when a push was last sent, and **overdue** when a due delivery has waited more than 5 minutes (nothing is sending). Push that isn't configured is shown as such, never as an error. A stopped sender with nothing to send only shows once something is due.
  - Backups: the latest run and the latest successful one. **Overdue** when the newest successful backup is older than the operational setting `backup_max_age_hours` (default 26 hours; 0 turns the check off).
  - Both are in `GET /api/v1/admin/system-status.php` and `/metrics.php` for your own monitoring. Neither affects `/health.php` or `/ready.php`. The System status card and the Operational settings field follow in a later release; until then, change the setting with `POST /api/v1/admin/settings/update.php`.
- **The maintenance maximum age is an operational setting** (API; the Operational settings field follows). ([#312](https://github.com/Thiesi/ChitChat/issues/312), [#314](https://github.com/Thiesi/ChitChat/pull/314)) Until you save a value, `MAINTENANCE_MAX_AGE_HOURS` (default 26) still applies, so upgrading changes nothing. Clearing the setting returns to it.
- **Search in one room** (API; the web's room filter follows). ([#283](https://github.com/Thiesi/ChitChat/issues/283), [#318](https://github.com/Thiesi/ChitChat/pull/318)) Message search accepts a room. A room you can't search answers exactly like one that doesn't exist.
- **"Announce new messages"** under You → Appearance: All, Only messages to me (mentions, pings and direct messages), or Off, saved on the device. ([#171](https://github.com/Thiesi/ChitChat/issues/171), [#292](https://github.com/Thiesi/ChitChat/pull/292))
- **For app developers, all additive:**
  - **Settled resume** for the event stream: `GET /api/v1/events/stream.php?resume=settled`, advertised as `capabilities.realtime_settled_resume`. In this mode the SSE `id:` is a resume position, not the event's identity. Store only that position, and drop resent events by `data.id`. `rooms/list.php` and the join response add `unread_settled_message_id` and `unread_counted_ids` for exact live unread counting. Without the parameter, nothing changes. See [`docs/api/realtime.md`](../api/realtime.md) ([#286](https://github.com/Thiesi/ChitChat/issues/286), [#291](https://github.com/Thiesi/ChitChat/pull/291)).
  - Ownership flags: `moderation.room.can_transfer_ownership` on the profile card, and `can_transfer_ownership` and `can_take_ownership` in the room administration snapshot. They mean "allowed now, after step-up", and they consider a ban only for viewers who can see bans ([#306](https://github.com/Thiesi/ChitChat/pull/306)).
  - Search: optional `room_id`, and `excerpt_matches` (match offsets in UTF-16 code units) ([#318](https://github.com/Thiesi/ChitChat/pull/318)).
  - System status: `push` and `backups`. Settings: `backup_max_age_hours`, `maintenance_max_age_hours` and `maintenance_max_age_source`. Send `maintenance_max_age_hours` only when an administrator changed it, or the environment fallback is frozen ([#313](https://github.com/Thiesi/ChitChat/pull/313), [#314](https://github.com/Thiesi/ChitChat/pull/314)).

## Changed

- **Stewardship pages in their own look (Lantern redesign S6).** ([#172](https://github.com/Thiesi/ChitChat/issues/172); [#307](https://github.com/Thiesi/ChitChat/pull/307), [#311](https://github.com/Thiesi/ChitChat/pull/311), [#319](https://github.com/Thiesi/ChitChat/pull/319))
  - Administration, Operational settings, System status, the Moderation queue, DM inspection and Revision review use the calm Dusk blue for their actions. Destructive actions stay red, and the chat keeps its warm colours.
  - Notices about sensitive access now say plainly what opening content means and what the audit log records.
- **No more browser pop-ups for confirmations on You and the stewardship pages.** ([#292](https://github.com/Thiesi/ChitChat/pull/292), [#307](https://github.com/Thiesi/ChitChat/pull/307), [#311](https://github.com/Thiesi/ChitChat/pull/311), [#319](https://github.com/Thiesi/ChitChat/pull/319))
  - Removing a passkey, new recovery codes, removing the authenticator app, turning off MFA, removing someone's profile picture, signing someone out everywhere, banning, resetting a password, deleting a room, removing a member, lockdown sign-out, the icon reset, the authenticator-key switch and dismissing a moderation case all ask in ChitChat's own dialog.
  - Saving Operational settings asks one question listing only the consequences that apply.
  - What each action does, and every confirmation step, is unchanged. Editing and deleting chat messages and renaming a passkey still use the browser's prompts; they follow in S7.
- **The search excerpt centres on the match.** A message longer than 320 characters now shows up to 320 characters around its first match, with "…" where it was cut, instead of always its beginning. ([#318](https://github.com/Thiesi/ChitChat/pull/318))

## Fixed

- **A message saved a moment late is no longer skipped.** ([#286](https://github.com/Thiesi/ChitChat/issues/286); [#291](https://github.com/Thiesi/ChitChat/pull/291), [#298](https://github.com/Thiesi/ChitChat/pull/298)) Two messages sent at nearly the same time could reach the event stream out of order. A reconnect at the wrong moment then skipped one until the page was reloaded. The web client now uses settled resume: nothing is skipped, and nothing is shown or counted twice.
- **Open tabs recover after an upgrade.** ([#301](https://github.com/Thiesi/ChitChat/issues/301), [#308](https://github.com/Thiesi/ChitChat/pull/308)) During an upgrade a site briefly answers "unavailable", and browsers then gave up on the live connection for good: open tabs said "Reconnecting" until reloaded. They now reconnect by themselves (waiting 1 s, growing to 30 s), resume where they left off, and sign out only if the session really ended. A page restored with Back reconnects the same way, and never shows a stale "Live" ([#323](https://github.com/Thiesi/ChitChat/issues/323), [#325](https://github.com/Thiesi/ChitChat/pull/325)).
- **Leaving or going Back is quiet.** ([#270](https://github.com/Thiesi/ChitChat/issues/270), [#320](https://github.com/Thiesi/ChitChat/pull/320), [#324](https://github.com/Thiesi/ChitChat/pull/324)) Requests cut short by leaving a page no longer show errors, and a page restored with Back works at once, including You, which loads again.
- **DM inspection can be submitted again.** Choosing the two people used to block the form. ([#319](https://github.com/Thiesi/ChitChat/pull/319))
- **You:** clicking a section before the page finished loading, or a failed load, no longer leaves an empty page; a failed load says so and offers Try again. The section list no longer shifts under the pointer while the page loads, which could swallow a click. ([#292](https://github.com/Thiesi/ChitChat/pull/292), [#317](https://github.com/Thiesi/ChitChat/pull/317), [#321](https://github.com/Thiesi/ChitChat/pull/321))
- **Profile card actions keep their result.** After confirming Remove, Ban or Sign out, the card stays open and shows what happened. ([#303](https://github.com/Thiesi/ChitChat/pull/303))
- **Keyboard and screen-reader fixes** in Administration and System status: named role selects, a labelled user dialog, and a reachable rate-limit table. ([#307](https://github.com/Thiesi/ChitChat/pull/307), [#311](https://github.com/Thiesi/ChitChat/pull/311))

## What to evaluate

Operators staging this release should check that:
- a room owner can hand a room to a member from the profile card, and an administrator can take over a room from Administration → Rooms;
- `GET /api/v1/admin/system-status.php` (or `/metrics.php`) reports `push` and `backups`, and that `backups.status` turns `ok` after the next `chitchat-backup` run;
- a tab left open during the upgrade goes back to "Live" by itself afterwards;
- Administration, Operational settings, System status and the moderation pages work on a desktop and a phone.

## Database changes

Both migrations are forward-only:
- `0059_push_backup_health.sql`: the `backup_runs` table, the `backup_max_age_hours` setting (default 26), and an index on sent push deliveries. The index is built without `CONCURRENTLY`, so writes to `push_deliveries` wait while it's built; adding the column briefly locks the one-row `system_settings` table.
- `0060_maintenance_max_age_setting.sql`: the optional `maintenance_max_age_hours` setting (empty, so the environment value keeps applying; adding the column briefly locks `system_settings`).

Run the upgrade with the site stopped, as in the steps below.

## Operator notes

- **No configuration changes.**
- **Nobody is signed out** by this upgrade.
- **Backups after upgrading:** System status shows backups as **unknown** until `bin/chitchat-backup` next runs, then the result of that run.
  - If your backups don't go through `bin/chitchat-backup` (a host snapshot or your own `pg_dump`), ChitChat can't see them: set `backup_max_age_hours` to 0 with `POST /api/v1/admin/settings/update.php` (a Super-Administrator, with step-up; the Operational settings field follows).
  - Recording needs the backup's database role to have `INSERT` and `DELETE` on `backup_runs` (the newest 100 runs are kept) and `USAGE` on `backup_runs_id_seq`; the instance's normal role has them. Without them the backup still succeeds, prints "Warning: backup run not recorded" to its log, and shows as unknown.
  - "Unknown" also counts as overdue while tracking is on, so right after the upgrade `chitchat_backup_overdue` is 1 in `/metrics.php` until the first `chitchat-backup` run on v3.10.0. If you alert on it, expect that, or set `backup_max_age_hours` to 0 until then.
- **Web database sessions** now end after 60 seconds idle inside a transaction. That's a session setting ChitChat applies itself; nothing to configure. Optionally, also set PostgreSQL's `idle_in_transaction_session_timeout` for other roles (see `INSTALL.md`).
- Continue backing up PostgreSQL and attachment storage together.

## Upgrade from v3.9.0

1. Stop application traffic (see `INSTALL.md`, Upgrading), and back up PostgreSQL and attachment storage together.
2. Deploy `v3.10.0` source.
3. Run:
   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   ```
   `composer migrate` applies `0059` and `0060`.
4. Reload PHP-FPM, and restart the push dispatcher listener if you run one.
5. Verify `/health.php`, `/ready.php`, and that `GET /api/v1/session.php` reports `application.version` `3.10.0`.

Upgrading from before `v3.9.0` also applies that release's migrations (`0056` to `0058`); read its release notes first, including the owner check.

## Known limitations

Unchanged from `v3.9.0`. In addition:
- The redesign continues: a final sweep of dialogs, empty states and copy (S7) follows.
- The System status page doesn't show Push and Backups yet, Operational settings has no fields for the two max ages yet, and web search has no room filter yet; all three follow in a later release. The API already provides them.
- Most room routes still answer a private room you can't see differently from a missing one (403 instead of 404); only search already answers alike. The next release fixes this ([#326](https://github.com/Thiesi/ChitChat/issues/326)), which changes those error codes; app developers have been told.
