# ChitChat v1.2.0-rc.1

`v1.2.0-rc.1` is the first release candidate for ChitChat v1.2.0. It is intended for controlled evaluation, deployment rehearsal, and upgrade testing; `v1.1.0` remains the supported stable baseline until v1.2.0 is released.

This is an in-place application upgrade from `v1.1.0`. It applies forward-only database migrations `0014` through `0017`; after migration, do not run older ChitChat source against the upgraded database.

## Highlights

### Configurable and observable throttling

- Authentication, account, messaging, upload, invitation, search, inspection, revision-review, restoration, and MFA paths use bounded named policies loaded from deployment environment variables.
- Existing limits remain enforced, formerly unbounded sensitive paths now have deliberately generous controls, and configuration stays outside the browser administration surface.
- Administrator status and Prometheus expose effective policies and aggregate allowed/rejected decisions without account, IP, room, message, search-term, or request-body identifiers.

### Supported backup and restore

- `chitchat-backup`, `chitchat-verify-backup`, and `chitchat-restore` bind PostgreSQL and attachment storage into one versioned manifest-driven backup set.
- Each set records application version, ordered migrations, database metadata, attachment inventory, tool versions, exact sizes, and SHA-256 checksums without storing the database password.
- Restore targets new database and attachment names by default, stages extraction, verifies restored inventory and migration state, and requires explicit flags before replacing existing or configured production targets.

### Account closure and restoration

- Account closure requires recent privileged step-up and immediately invalidates sessions, revokes global roles, denies normal login, and removes live presence and SSE leases.
- A fixed 14-day cooling-off period reserves the username and provides an explicit independently throttled restoration flow using current credentials and, where configured, the account's passkey or recovery code.
- Expired closures are finalized through ordinary maintenance by tombstoning profile identifiers and credentials while retaining shared conversation history, revisions, attachment evidence, attribution, bans, and audits according to retention policy.
- The final active Super-Administrator cannot close their account.

### Passkey multi-factor authentication

- Optional password-first MFA supports multiple labelled WebAuthn passkeys and ten one-time recovery codes.
- ChitChat validates exact RP ID, origin, challenge and ceremony type, requires user presence and verification, supports ES256 and RS256 credentials, tracks backup state, and validates nonzero signature counters.
- Passkeys and recovery codes complete ordinary login, privileged step-up, and closure restoration; MFA-enabled accounts cannot fall back to password-only step-up.
- Super-Administrators may require passkey MFA for every global administrative role, with transactional activation checks and a PostgreSQL invariant for later role grants.
- Passkeys remain disabled until both `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGIN` are configured.

### Participant-facing privacy notifications

- Durable notifications disclose administrative revision review, moderator room-message deletion, administrative password reset, and material installation-policy changes to affected participants.
- PostgreSQL derives them from append-only audit records in the same transaction, so the restricted action cannot commit without its bounded participant disclosure.
- The notification center provides pagination, individual and bulk read state, and a capped unread badge.
- Notifications do not copy message bodies, revisions, administrator reasons, usernames, IP addresses, credentials, passkey data, or recovery material.

### Accessibility and visual regression

- Chromium runs pinned axe-core WCAG A/AA analysis across authentication, restoration, chat, direct messages, account, and notification surfaces.
- Automated coverage includes 640- and 320-CSS-pixel reflow, forced-colors affordances, reduced-motion behavior, and three deliberately stable Linux screenshot baselines.
- Chromium, Firefox, and WebKit retain their independent functional, structural, and keyboard journeys.
- A documented human procedure covers NVDA, VoiceOver, keyboard-only operation, 200%/400% zoom, Windows contrast themes, and reduced motion. Automated success does not constitute manual assistive-technology sign-off.

## What to evaluate

Operators evaluating this release candidate should exercise:

- a fresh installation and an in-place upgrade from an actual `v1.1.0` archive;
- existing login, room, direct-message, attachment, moderation, inspection, export, retention, maintenance, and reverse-proxy SSE behavior;
- effective rate-limit settings and privacy-preserving counters under representative traffic;
- creation, verification, off-host retention, and isolated restore of a complete PostgreSQL-plus-attachment backup set;
- closure, immediate access denial, restoration before the deadline, final-Super-Administrator protection, and maintenance dry-run reporting;
- passkey enrollment, additional credentials, recovery-code rotation and one-time consumption, passkey login, MFA step-up, restoration, and any administrative-MFA policy;
- participant notification recipient selection, unread state, material-policy-change suppression for no-op updates, and tombstone cleanup;
- narrow/zoomed layouts, keyboard navigation, contrast themes, reduced motion, and the documented NVDA and VoiceOver journeys on real target platforms.

Record defects against `v1.2.0-rc.1`. Do not move or recreate the release tag; fixes require a later release-candidate or stable version.

## Database changes

The upgrade applies these forward-only migrations:

- `0014_rate_limit_observability.sql` — aggregate rate-limit decision state;
- `0015_account_closure.sql` — closure lifecycle, saved role state, restoration, and database-bound tombstoning;
- `0016_mfa_passkeys.sql` — WebAuthn credentials, challenges, recovery codes, and administrative-MFA invariants;
- `0017_privacy_notifications.sql` — durable account notification state and audit-derived triggers.

Back up PostgreSQL and attachment storage together before migration. Rolling back requires restoring a matching pre-upgrade database and attachment backup; there is no down-migration path.

## Upgrade from v1.1.0

1. Stop or drain application writes.
2. Back up PostgreSQL and the complete attachment-storage directory together using the existing operating procedure, and verify the backup before deployment.
3. Preserve `.env` and the existing attachment-storage path.
4. Deploy `v1.2.0-rc.1` source.
5. Compare `.env` with `.env.example`. Retain existing values; add rate-limit overrides only deliberately, and configure WebAuthn only after choosing a durable HTTPS RP ID and origin.
6. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   composer maintenance:dry-run
   ```

7. Review the effective rate-limit policies in Administrator system status.
8. Create and verify a new first-class backup set, then perform an isolated restore rehearsal before relying on the new tooling operationally.
9. Verify `/health.php`, `/ready.php`, login, room and direct-message history, attachments, SSE through the production reverse proxy, account export, system status, account closure/restoration, privacy notifications, and any enabled passkey flow.

The automated release rehearsal installs the published `v1.1.0` archive, seeds representative data, preserves PostgreSQL and attachment bytes through backup/restore, advances to the release-candidate migrations, and verifies retained application behavior.

## Fresh installation

Follow `INSTALL.md`. Expose only `public/`, keep attachment and backup storage outside the web root, use HTTPS and secure cookies, provide enough PHP workers for open SSE requests, schedule maintenance and backups, and document the installation's inspection, retention, closure, MFA, notification, and restore policies before onboarding users.

## Security and privacy defaults

- Direct messages are server-side PostgreSQL records and are **not end-to-end encrypted**.
- Administrative canonical DM inspection remains enabled for Super-Administrators by default, requires recent step-up plus a reason, and audits every successful page.
- Historical revision review remains disabled by default and uses an authorization policy independent from ordinary DM inspection and moderation roles.
- Retention values of `0` mean permanent retention until a Super-Administrator changes policy and maintenance runs.
- Account closure removes private access and privileges but does not erase shared retained conversation history or immutable evidence.
- Passkeys are opt-in at deployment level; existing password-only installations behave as before while WebAuthn configuration is absent.
- Participant notifications disclose selected sensitive actions without duplicating restricted content or reasons.
- Backup encryption, access control, off-host retention, restore authorization, maintenance scheduling, and release-specific manual assistive-technology validation remain operator responsibilities.

## Validation required for publication

The exact merged release commit must pass:

- locked Composer and npm dependency audits;
- PHP lint, JavaScript and stabilization-shell syntax checks, and PHPStan level 8;
- every migration and the complete PHPUnit suite against PostgreSQL 16;
- maintenance dry-run;
- the full two-session release journey independently in Chromium, Firefox, and WebKit;
- structural and keyboard accessibility checks in all three engines;
- Chromium axe-core, reflow, forced-colors, reduced-motion, virtual-WebAuthn-authenticator, and targeted screenshot checks;
- installation from the published `v1.1.0` archive followed by backup, restore, migration, and retained-data verification;
- the dedicated first-class backup rehearsal;
- authenticated unbuffered SSE delivery through real Nginx and PHP-FPM.

Publication validation checks those named results on the exact 40-character merge commit before the annotated tag and GitHub pre-release are created.

## Known limitations

- This is a release candidate, not yet an unconditional production recommendation; compatible fixes may precede `v1.2.0`.
- The supported deployment target remains one application server; horizontal scaling and Redis-backed event delivery are not implemented.
- PostgreSQL is the only supported database.
- Direct messages are not end-to-end encrypted.
- Automated accessibility coverage is not a complete manual WCAG audit and does not prove NVDA or VoiceOver behavior.
- Maintenance, backup scheduling, alerting, retention decisions, and policy disclosure remain operator responsibilities.
- No supported upgrade path exists from the incomplete legacy `v0.10.25` snapshot.

Detailed individual changes are listed in `CHANGELOG.md`.
