# ChitChat v1.3.0

`v1.3.0` is the fourth stable release of the clean ChitChat reconstruction. It promotes the evaluated `v1.3.0-rc.1`/`v1.3.0-rc.2` feature set — participant search, a moderation queue, and replies/mentions — and adds message reactions on top before stabilizing.

Reactions did not go through its own release-candidate evaluation window. It was validated the way every merge to `main` already is: full CI (the complete PHPUnit integration suite plus the Chromium, Firefox, and WebKit browser matrix) on each of its two pull requests, rather than a dedicated pre-release soak period. Operators who want release-candidate-style evaluation of reactions specifically before adopting `v1.3.0` should exercise the reactions flows below in a staging deployment first.

This is an in-place application upgrade from `v1.2.0`, or from an existing `v1.3.0-rc.1`/`v1.3.0-rc.2` deployment. It applies forward-only database migrations `0018` through `0021`; after migration, do not run older ChitChat source against the upgraded database.

## Highlights

### Authorization-aware participant message search

- Search current, undeleted room and direct-message bodies using PostgreSQL full-text search, with combined, room-only and direct-only scopes and bounded pagination.
- Room discoverability, membership, invitation, minimum-age and DM-participant authorization are enforced inside the query itself; the query never joins retained revision bodies.
- Search terms travel in a CSRF-protected POST body and are excluded from URLs, ChitChat audits, rate-limit identifiers, aggregate counters and Prometheus labels.
- Results link to the exact message through ordinary authorized history APIs.

### Participant reporting and moderation queue

- Participants may report one specific visible, undeleted room message or incoming direct message.
- Reports aggregate by canonical message while allowing each participant one report per case, and preserve an immutable exact-message snapshot so later edits or ordinary retention cannot erase active evidence.
- Room owners and moderators see only cases from rooms they currently moderate; global moderation roles may review DM cases but receive only the submitted exact-message snapshot, never surrounding private history or attachment bytes.
- Cases support open, in-review, resolved and dismissed states with explicit assignment and bounded outcome notes.
- A participant's own submitted reports appear in their personal-data export without disclosing other reporters, queue assignments or private moderator notes.

### Replies and mentions

- Durable reply references on room and direct messages, resolved through the same authorization-scoped read path as ordinary history. A reply cannot point across rooms or DM threads.
- `@username` mentions, plus room-scoped `@room`/`@here` broadcast mentions, resolved and authorized once at send time — never by trusting the composed text. An unauthorized or unresolvable token renders as plain text and never notifies anyone.
- Durable `mentioned` participant notifications with a human-readable timeline entry and a deep link to the exact message.
- Reply and `@mention` support in both composers: a reply banner with cancel, a quoted click-to-scroll preview, `@mention` autocomplete, and highlighting limited strictly to mentions the server actually resolved.
- Reply-target and caption-mention support on attachment uploads, matching ordinary text messages.
- A dedicated `RATE_LIMIT_ROOM_BROADCAST_MENTION` policy throttles `@room`/`@here` independently of ordinary room-send limits.

### Reactions

- A small controlled emoji vocabulary — 👍 ❤️ 😂 😮 😢 🎉 — with idempotent add/remove enforced by a database `UNIQUE (message_id, user_id, emoji)` constraint rather than application logic.
- Reacting requires exactly the same authorization as reading the message; there is no new authorization concept, no separate rate-limit policy, and no new realtime transport.
- Reactor identity is visible the same way message authorship already is: a message's `reactions` carry each emoji's reacting participants by id and username, not just an aggregate count. See [ADR 0005](../architecture/0005-reactions.md) for the full design rationale.
- Reacting to an already-deleted message is rejected with `409 message_already_deleted`; reacting to an existing direct message stays available after a block, matching how reply previews already behave.
- A reaction bar in both browser clients shows pills for emoji already in use (clicking toggles your own reaction) plus an "Add reaction" control for the full vocabulary, updated live through a new `message_reaction_changed` realtime event.

## What to evaluate

Operators staging this release before a production upgrade should exercise everything listed in `v1.3.0-rc.1` and `v1.3.0-rc.2`'s evaluation guidance (search, reporting, moderation, replies, mentions), plus, for reactions specifically:

- adding and removing each of the six supported emoji on a room message and a direct message, confirming the action is idempotent (repeating it doesn't create duplicate state) and that removing an absent reaction is a harmless no-op;
- confirming a participant who cannot read a message (not a room member, not a DM participant) cannot react to it;
- confirming reacting to an already-deleted message is rejected, and that reacting to an existing direct message still works after blocking the other participant;
- confirming reactions update live across two open sessions via the `message_reaction_changed` event, and that the reactor list shown matches who actually reacted;
- existing login, room, direct-message, attachment, search, moderation, reply, mention, inspection, export, retention, maintenance, and reverse-proxy SSE behavior remaining unaffected.

## Database changes

Upgrading from `v1.2.0` applies these forward-only migrations:

- `0018_message_search.sql` — authorization-aware full-text search indexes over current, undeleted room and direct-message bodies;
- `0019_moderation_reports.sql` — report and moderation-case tables, immutable evidence snapshots, assignment and resolution state;
- `0020_replies_mentions.sql` — non-cascading reply references on room and direct messages, cascading per-kind mention tables, and a `mentioned` notification kind;
- `0021_reactions.sql` — cascading per-kind reaction tables with a `UNIQUE (message_id, user_id, emoji)` constraint, and the `message_reaction_changed` realtime event type.

An installation already migrated through `0020_replies_mentions.sql` (i.e. `v1.3.0-rc.2`) has only `0021_reactions.sql` left to apply. Running `composer migrate` remains safe and confirms the existing migration state either way.

Back up PostgreSQL and attachment storage together before any deployment. Rolling back requires restoring a matching pre-upgrade database and attachment backup; there is no down-migration path.

## Upgrade from v1.2.0

1. Stop or drain application writes.
2. Create and verify a complete PostgreSQL-plus-attachment backup set.
3. Preserve `.env` and the existing attachment-storage path.
4. Deploy `v1.3.0` source.
5. Compare `.env` with `.env.example`. Retain existing values.
6. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   composer maintenance:dry-run
   ```

7. Verify `/health.php`, `/ready.php`, login, room and direct-message history, attachments, SSE through the production reverse proxy, participant search, moderation reporting, replies/mentions, and reactions.

## Promote an existing v1.3.0-rc.1 or v1.3.0-rc.2 installation

1. Create and verify a complete PostgreSQL-plus-attachment backup set.
2. Preserve `.env` and the attachment-storage path.
3. Deploy `v1.3.0` source.
4. Change an explicitly pinned `APP_VERSION` value to `1.3.0`, or omit it to use the stable default.
5. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   composer maintenance:dry-run
   ```

6. Confirm `composer migrate` applies only the migrations not already present on that installation (`0021_reactions.sql` for an existing `rc.2` deployment).
7. Verify health, readiness, login, representative room/DM/attachment behavior, SSE through the production reverse proxy, maintenance status, and reactions.

No schema rollback, data conversion, or configuration redesign is required for promotion.

## Fresh installation

Follow `INSTALL.md`. Expose only `public/`, keep attachment and backup storage outside the web root, use HTTPS and secure cookies, provide enough PHP workers for open SSE requests, schedule maintenance and backups, and document the installation's inspection, retention, closure, MFA, notification, and restore policies before onboarding users.

## Security and privacy defaults

- Direct messages are server-side PostgreSQL records and are **not end-to-end encrypted**.
- Search never returns retained revision bodies, and search terms are kept out of URLs, audits, rate-limit identifiers, and aggregate metrics.
- Moderation evidence is immutable once submitted; room-scoped moderators cannot see cases outside rooms they currently moderate, and DM case reviewers receive only the submitted snapshot.
- Reply previews resolve through the same authorization-scoped read path as ordinary history; a reply cannot be used to read a message outside its own room or conversation.
- Mentions are authorized independently at send time, individually and for broadcasts; a mention notification never discloses another participant's message body.
- Reacting requires the same authorization as reading the message; reactor identity is visible the same way message authorship already is, an explicit, confirmed tradeoff rather than a silent default (see ADR 0005).
- Backup encryption, access control, off-host retention, restore authorization, maintenance scheduling, and release-specific manual assistive-technology validation remain operator responsibilities.

## Validation required for publication

The exact merged release commit must pass:

- locked Composer and npm dependency audits;
- PHP lint, JavaScript and stabilization-shell syntax checks, and PHPStan level 8;
- every migration and the complete PHPUnit suite against PostgreSQL 16;
- maintenance dry-run;
- the full two-session release journey independently in Chromium, Firefox, and WebKit;
- structural and keyboard accessibility checks in all three engines;
- Chromium axe-core, reflow, forced-colors, reduced-motion, and targeted screenshot checks;
- installation from the published `v1.2.0` archive followed by backup, restore, migration, and retained-data verification;
- the dedicated first-class backup rehearsal;
- authenticated unbuffered SSE delivery through real Nginx and PHP-FPM.

Publication validation checks those named results on the exact 40-character merge commit before the annotated `v1.3.0` tag and stable GitHub release are created.

## Known limitations

- The supported deployment target remains one application server; horizontal scaling and Redis-backed event delivery are not implemented.
- PostgreSQL is the only supported database.
- Direct messages are not end-to-end encrypted.
- No reply/mention/reaction support in administrative DM inspection or revision-review surfaces.
- Automated accessibility coverage is not a complete manual WCAG audit and does not prove NVDA or VoiceOver behavior.
- Maintenance, backup scheduling, alerting, retention decisions, and policy disclosure remain operator responsibilities.
- No supported upgrade path exists from the incomplete legacy `v0.10.25` snapshot.

Detailed individual changes are listed in `CHANGELOG.md`.
