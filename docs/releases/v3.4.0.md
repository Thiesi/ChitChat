# ChitChat v3.4.0

`v3.4.0` is the second native-client readiness release. It adds what Google Play's user-generated-content policy expects from a chat app (installation rules with agreement, reporting a person), self-service password recovery, and image dimensions and previews. API v1 changes are additive. Existing installations behave as before until an administrator publishes documents, and existing clients keep working. It adds four forward-only database migrations, so back up before upgrading.

## Project status: feature-complete

This release does not change [project status](../README.md#project-status-feature-complete). It ships specific, concretely proposed additions requested by the ChitChat Mobile client, tracked in [#163](https://github.com/Thiesi/ChitChat/issues/163). See [`docs/roadmap.md`](../roadmap.md).

## Added

- **Community rules, privacy policy and legal notice.** ([#160](https://github.com/Thiesi/ChitChat/issues/160); [#179](https://github.com/Thiesi/ChitChat/pull/179), [#180](https://github.com/Thiesi/ChitChat/pull/180))
  - Super-Administrators can publish community rules and a privacy policy, either written in ChitChat (Markdown, hosted at `/rules.php` and `/privacy.php`) or as a link to their own site, plus an optional legal-notice link.
  - Members agree to the rules at registration and provider sign-up, and guests by starting a visit. The privacy policy is linked and never ticked.
  - The server versions the documents. A small fix asks nobody again. A material change asks members to agree before they write again: reading, account, safety, moderation and administration stay available meanwhile.
  - A material privacy-policy change sends an information-only notification, which is never pushed.
  - Discovery is available in `session.php` (`policies`, `user.rules`). New error codes: `rules_acceptance_required`, `rules_version_outdated`.
- **Reporting a person.** ([#159](https://github.com/Thiesi/ChitChat/issues/159); [#181](https://github.com/Thiesi/ChitChat/pull/181), [#182](https://github.com/Thiesi/ChitChat/pull/182))
  - People can report an offensive username, a profile picture or behaviour from a profile card or a direct-message header, not only a single message.
  - A report made from a room goes to that room's moderators; other reports go to global moderators. A copy of the picture at report time is kept as evidence and shown to moderators blurred until revealed.
  - After reporting, people are offered ignore and block right away. The moderation queue can filter by messages or people, and gains a "Profile picture removed" outcome.
- **Self-service password recovery.** ([#155](https://github.com/Thiesi/ChitChat/issues/155); [#183](https://github.com/Thiesi/ChitChat/pull/183), [#184](https://github.com/Thiesi/ChitChat/pull/184))
  - Every password account gets a recovery key, shown once at registration and replaceable from Account (with confirmation of identity).
  - "Forgot password?" lets members set a new password with their username and recovery key, with no administrator involved. Accounts with a second factor must still pass it, and a reset never grants elevated access. Every other session is signed out, and a new key is shown.
  - Existing accounts see a dismissible reminder to create a key. An administrator's password reset invalidates the member's key.
- **Image dimensions and previews.** ([#158](https://github.com/Thiesi/ChitChat/issues/158), [#186](https://github.com/Thiesi/ChitChat/pull/186))
  - Image attachments report their oriented display dimensions and, for new uploads, a bounded WebP preview (1024 px long edge, metadata stripped, GIFs as a still frame) at `variant=preview` on the existing download routes.
  - The browser client keeps showing originals for now; native clients can use previews immediately.

## Fixed

- **Warnings no longer corrupt downloads.** With PHP error display on, a harmless warning was written ahead of attachment downloads, the event stream, metrics output and one administration response. Those warnings are gone, and a test guards against their return. ([#186](https://github.com/Thiesi/ChitChat/pull/186))
- **Changing a password and a recovery reset can't interleave.** An ordinary password change now checks the current password and session inside the same transaction. ([#183](https://github.com/Thiesi/ChitChat/pull/183))

## Development

- Playwright can start and stop a local PHP server for the mocked browser specs (`CHITCHAT_PHP_SERVER_PORT`, opt-in) ([#185](https://github.com/Thiesi/ChitChat/pull/185)).

## New configuration

- **`APP_ORIGIN`** (optional, recommended): the installation's canonical public origin, for example `https://chat.example.org`. It's used for absolute links to hosted documents, and falls back to `OIDC_REDIRECT_ORIGIN`, then `WEBAUTHN_ORIGIN`, then the request host. Set it behind a TLS-terminating proxy, so native clients receive `https://` links.

## What to evaluate

Operators staging this release should check that:

- sign-in, registration (which now shows the recovery key), rooms, direct messages and attachments work as before;
- with no documents published, nothing asks anyone to agree to anything;
- publishing test rules in Operational settings shows them at `/rules.php`, and a new registration asks for agreement;
- "Forgot password?" resets a test account with its recovery key;
- reporting a person from a profile card reaches the moderation queue.

## Database changes

All four migrations are forward-only:

- `0041_installation_policies.sql`: policy documents and rules-acceptance records, with acceptance records erased when an account is closed.
- `0042_person_reports.sql`: person cases with an immutable scope, picture snapshots (at most 128 KiB each) and new categories and outcome.
- `0043_password_recovery.sql`: recovery-key hashes, erased when an account is closed.
- `0044_attachment_image_previews.sql`: nullable image dimension and preview columns on both attachment tables. Existing files aren't processed.

## Operator notes

- **Previews** need PHP's GD extension with WebP support. For previews of large photos, give PHP-FPM a `memory_limit` of at least `256M`; with the common `128M`, large photos still upload and report dimensions, but get no preview.
- **Previews for older images** are created only by an explicit, operator-run backfill command (dry-run first, small batches). Deploying doesn't start it, and running it is optional. See [image-preview backfill](../operations/image-preview-backfill.md).
- **Backups** must keep covering PostgreSQL and attachment storage together, which now includes preview files.
- **Don't publish hosted rules or a privacy policy on a public installation before upgrading every web node to this version.** Older nodes would neither show nor enforce them.

## Upgrade from v3.3.0

1. Back up PostgreSQL and attachment storage together.
2. Deploy `v3.4.0` source. Optionally set `APP_ORIGIN`, and review PHP's `memory_limit` and GD/WebP support for previews.
3. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   ```

   `composer migrate` applies `0041` to `0044`.
4. Verify `/health.php`, `/ready.php`, and that `GET /api/v1/session.php` reports `application.version` `3.4.0`.

Upgrading from before `v3.3.0` also applies that release's migration, `0040_room_activity_index.sql`; see its notes.

## Validation required for publication

The exact merged release commit must pass:

- locked Composer and npm dependency audits;
- PHP lint, JavaScript and stabilization-shell syntax checks, JavaScript unit tests, and PHPStan level 8 on PHP 8.2, 8.3 and 8.4;
- the complete PHPUnit suite against PostgreSQL 16 on PHP 8.2, 8.3 and 8.4;
- the full browser journey independently in Chromium, Firefox and WebKit;
- structural and keyboard accessibility checks in all three engines, and axe-core checks of both themes in Chromium;
- the dedicated first-class backup rehearsal;
- authenticated unbuffered SSE delivery through real Nginx and PHP-FPM.

Publication validation checks those named results on the exact 40-character merge commit before the annotated `v3.4.0` tag and stable GitHub release are created.

## Known limitations

Unchanged from `v3.3.0`. In addition:

- The browser client doesn't use image previews yet (planned with the presentation overhaul).
- The native-authentication capabilities stay `false` until #145 and #146 ship.
