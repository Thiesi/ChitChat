# ChitChat v2.0.1

`v2.0.1` is a bug-fix release on top of the final planned `v2.0.0` release. It adds no new feature and applies no database migration. It fixes findings from an independent post-release security review of the authentication and WebAuthn implementation.

This is an in-place application upgrade from `v2.0.0`. There is no new migration to apply; operators may deploy `v2.0.1` over `v2.0.0` without a database backup/restore cycle beyond ordinary operational practice.

## Project status: feature-complete

This release does not change [project status](../README.md#project-status-feature-complete). ChitChat remains feature-complete: `v2.0.1` is exactly the kind of bug-fix work the project's maintenance-only policy reserves room for, not a resumption of open-ended roadmap work. See [`docs/roadmap.md`](../roadmap.md).

## Fixed

All findings below came from one independent security review of `src/Auth/`, `src/Account/AccountClosureService.php`, `src/Http/Request.php`, and the admin endpoints that call into them. Full detail, exploit scenarios, and rationale are recorded in each linked issue.

- **WebAuthn sign-counter clone detection could be permanently disabled.** A cloned or replayed authenticator sending an assertion with `signCount = 0` after a nonzero stored counter was silently accepted, and the accepted zero value overwrote the server's high-water mark — permanently disabling clone detection for that credential from then on. The check now follows the WebAuthn spec's actual boundary: it only skips when *both* the stored and new counters are zero. ([#73](https://github.com/Thiesi/ChitChat/issues/73))
- **The login throttle let one attack vector lock out an unrelated victim.** Failed attempts were counted in one combined `username OR ip` bucket, so failures against a known username locked that account indefinitely, and failures from a shared IP (office NAT, VPN, CDN egress) could lock out every other user behind it. Username and IP are now two independently configurable rate-limit policies (`login`, `login_ip`), with the IP policy defaulting to a materially higher threshold to reduce false-positive collateral lockout. ([#74](https://github.com/Thiesi/ChitChat/issues/74))
- **No documented warning against fronting ChitChat with another proxy or CDN.** ChitChat deliberately reads only `REMOTE_ADDR`, never `X-Forwarded-For`, since it has no configured trusted-proxy allowlist. That's the right default, but nothing said the deployment's Nginx must be the component terminating the client's TCP connection. Putting anything else in front of it silently collapses every IP-based control (login/restoration throttles, the pending-MFA IP pin, per-IP rate limits, audit-log accuracy) onto one shared address. Documented prominently in `docs/operations/nginx-php-fpm.md`, cross-referenced from `INSTALL.md`, and noted directly on `Request::clientIp()`. ([#75](https://github.com/Thiesi/ChitChat/issues/75))
- **Username enumeration via a timing side channel.** A nonexistent username short-circuited before `password_verify`, while a real username always paid the full bcrypt cost — a timing gap in the hundreds of milliseconds, trivially measurable over a network. Both login and account-restoration now always run `password_verify` against a fixed dummy hash on a lookup miss. Account restoration also gained an independent per-IP throttle (`account_restore_ip`), since its prior per-username-and-IP key let one IP probe unlimited distinct usernames. ([#76](https://github.com/Thiesi/ChitChat/issues/76))
- **A `CborDecoder` duplicate-key check could be bypassed.** PHP silently coerces a numeric string array key (`"3"`) to an integer key (`3`), which let a crafted CBOR map (attacker-controlled input during WebAuthn ceremonies) present a string key and an integer key that collide after coercion without tripping the decoder's duplicate-key rejection. The check now also verifies via `array_key_exists`, which catches the coerced collision the typed-key tracking missed. ([#77](https://github.com/Thiesi/ChitChat/issues/77))
- **A NUL byte in a password crashed password hashing.** `password_hash()` throws an uncaught `ValueError` on an embedded NUL byte in PHP 8, which reached several unauthenticated and authenticated endpoints as an unhandled HTTP 500 instead of a normal validation error. `PasswordPolicy` now rejects control characters (including NUL) with a clean 400. ([#79](https://github.com/Thiesi/ChitChat/issues/79))
- **Admin ban, kick, and unban did not require privileged step-up.** Every other comparably sensitive administrative action (role changes, password resets) already required recently-verified step-up authentication; these three did not, so a hijacked admin session with no fresh step-up could ban or kick any non-super-admin account. They now require step-up, matching the rest of the admin surface. ([#80](https://github.com/Thiesi/ChitChat/issues/80))
- **`WEBAUTHN_ORIGIN` wasn't normalized, and credential ID length wasn't bounded.** A differently-cased origin (`HTTPS://Chat.Example.Com`) or one with an explicit default port (`:443`) failed every passkey ceremony via strict string comparison against the browser's always-lowercase, always-default-port-omitted origin — this failed closed, but silently. `WEBAUTHN_ORIGIN` is now normalized at configuration load. Separately, registration accepted credential IDs up to 65535 bytes where the WebAuthn spec caps them at 1023; registration now enforces that limit. ([#81](https://github.com/Thiesi/ChitChat/issues/81))

## Not changed

One finding from the same review, [#78](https://github.com/Thiesi/ChitChat/issues/78) (MFA recovery codes hashed with a single unsalted SHA-256 round rather than a slow password hash), was re-evaluated and closed without a code change. `docs/security/webauthn.md` already documents this as an intentional choice: recovery codes are 96 bits of random data, not a human-chosen secret, so salting or peppering provides no realistic security benefit against a space that large, and switching to a slow hash would have added a genuine per-attempt CPU cost (looping a bcrypt-class verification over up to ten codes) in exchange for that non-benefit. See the issue for the full reasoning.

## What to evaluate

Operators staging this release should exercise:

- passkey registration and login on an installation where `WEBAUTHN_ORIGIN` was previously configured with mixed case or an explicit default port, confirming ceremonies that previously failed now succeed;
- repeated failed logins against one username and, separately, from one shared IP, confirming the two throttles trip independently at their configured thresholds;
- account restoration after several failed attempts against different usernames from one IP, confirming the new per-IP throttle engages;
- an administrator banning, kicking, or unbanning a user, confirming the step-up dialog now appears exactly as it does for role changes and password resets;
- existing login, MFA, passkey, room, direct-message, attachment, search, moderation, reply, mention, reaction, inspection, export, retention, maintenance, and reverse-proxy SSE behavior remaining unaffected.

## Database changes

None. `v2.0.1` applies no migration.

## Upgrade from v2.0.0

1. Stop or drain application writes (optional for a bug-fix release with no migration, but recommended).
2. Deploy `v2.0.1` source.
3. Compare `.env` with `.env.example`; no new variables were introduced, though `login_ip` and `account_restore_ip` rate-limit thresholds may now be tuned independently via `RATE_LIMIT_LOGIN_IP_MAX_ATTEMPTS`/`RATE_LIMIT_LOGIN_IP_WINDOW_SECONDS` and `RATE_LIMIT_ACCOUNT_RESTORE_IP_MAX_ATTEMPTS`/`RATE_LIMIT_ACCOUNT_RESTORE_IP_WINDOW_SECONDS`.
4. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   ```

5. Verify `/health.php`, `/ready.php`, password login, MFA login when enabled, and the Administrator system-status page.

## Fresh installation

Follow `INSTALL.md`, which now also explains why an additional reverse proxy or CDN must not sit in front of the deployment's Nginx.
