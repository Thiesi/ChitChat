# ChitChat v2.2.0

`v2.2.0` is a maintenance release on top of `v2.1.0`. It lets a Super-Administrator rename the installation from the administration console and adds a small "Powered by ChitChat!" footer. It applies one forward-only database migration.

## Project status: feature-complete

This release does not change [project status](../README.md#project-status-feature-complete). ChitChat remains feature-complete. The additions below are specific, concretely requested changes of the kind the maintenance-only policy reserves room for, not a resumption of open-ended roadmap work. See [`docs/roadmap.md`](../roadmap.md).

## Added

- **An editable application name.** A Super-Administrator can rename the installation under **Operational settings → Application name**. ([#96](https://github.com/Thiesi/ChitChat/pull/96))
  - `APP_NAME` remains the server default and applies whenever the field is empty.
  - The change requires privileged step-up and is audited as `system.application_name_updated`, without notifying every account.
  - The name is used consistently in page titles and headings, passkey prompts, push notifications, personal-data exports, backup manifests, and the system-status page.
  - Several texts that still said "ChitChat" now use it: the search-result link, the recovery-code explanation, and the notifications, search, and revision-review page texts.
  - Pages fall back to `APP_NAME` if the database is unavailable. `/health.php` and the metrics realm always report `APP_NAME`. Machine identifiers such as the `chitchat-backup` and `chitchat-personal-data-export` format names are unchanged.
- **A "Powered by ChitChat!" footer.** A small line on every page links to the project repository. It names the software, independent of the installation's configured name. On the chat page it sits at the bottom of the sidebar. ([#97](https://github.com/Thiesi/ChitChat/pull/97))

## Maintenance

- A unit test that generated random passkey keys failed about once in 128 runs, because OpenSSL can return a key coordinate one byte short. The test now pads coordinates as authenticators do. Real authenticators were never affected. ([#96](https://github.com/Thiesi/ChitChat/pull/96))
- The visual regression test reports every changed layout in one run. ([#97](https://github.com/Thiesi/ChitChat/pull/97))

## What to evaluate

Operators staging this release should exercise:

- **Operational settings → Application name**: renaming the installation, confirming the new name appears in the chat page title and heading and on other pages after a reload, and clearing the field to return to `APP_NAME`;
- adding a passkey after a rename, confirming the browser prompt shows the new name;
- the footer link on the sign-in page, the chat sidebar (inside the Menu on phones), and the account page;
- existing login, MFA, passkey, registration, room, direct-message, attachment, search, moderation, reply, mention, reaction, inspection, export, retention, maintenance, and reverse-proxy SSE behavior remaining unaffected.

## Database changes

Upgrading from `v2.1.0` applies this forward-only migration:

- `0024_application_name.sql` adds the nullable `application_name` column to `system_settings`. `NULL` means `APP_NAME` applies, so the installation keeps its current name after migration.

Upgrading from an earlier `v2.x` release also applies `0023_registration_protection.sql` from `v2.1.0`. Back up PostgreSQL and attachment storage together before any deployment. Rolling back requires restoring a matching pre-upgrade database and attachment backup; there is no down-migration path.

## Upgrade from v2.1.0

1. Stop or drain application writes.
2. Create and verify a complete PostgreSQL-plus-attachment backup set.
3. Preserve `.env` and the existing attachment-storage path.
4. Deploy `v2.2.0` source.
5. Compare `.env` with `.env.example`; no new variables were introduced.
6. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   composer maintenance:dry-run
   ```

7. Verify `/health.php`, `/ready.php`, login, registration in a browser, the Operational settings page, room and direct-message history, attachments, and SSE through the production reverse proxy.

## Validation required for publication

The exact merged release commit must pass:

- locked Composer and npm dependency audits;
- PHP lint, JavaScript and stabilization-shell syntax checks, and PHPStan level 8 on PHP 8.2, 8.3, and 8.4;
- the complete PHPUnit suite against PostgreSQL 16 on PHP 8.2, 8.3, and 8.4;
- the full browser journey, including renaming the installation, independently in Chromium, Firefox, and WebKit;
- structural and keyboard accessibility checks in all three engines;
- the dedicated first-class backup rehearsal;
- authenticated unbuffered SSE delivery through real Nginx and PHP-FPM.

Publication validation checks those named results on the exact 40-character merge commit before the annotated `v2.2.0` tag and stable GitHub release are created.
