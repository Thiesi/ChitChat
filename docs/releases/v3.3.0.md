# ChitChat v3.3.0

`v3.3.0` is the first of the releases that prepare ChitChat for native clients, starting with the Android app ChitChat Mobile. Every change is additive to API v1: existing clients, including the browser client, keep working unchanged. It adds one forward-only database migration, an index, so back up before upgrading.

## Project status: feature-complete

This release does not change [project status](../README.md#project-status-feature-complete). It evaluates and ships specific, concretely proposed additions requested by the ChitChat Mobile client, tracked in [#163](https://github.com/Thiesi/ChitChat/issues/163). See [`docs/roadmap.md`](../roadmap.md).

## Added

- **Machine-readable retry delays.** ([#157](https://github.com/Thiesi/ChitChat/issues/157), [#165](https://github.com/Thiesi/ChitChat/pull/165))
  - HTTP 429 `rate_limited` and `login_throttled` responses now include `error.retry_after_seconds` and a standard `Retry-After` header with the same value, in whole seconds rounded up.
  - For sign-in, the value covers both the username and the address limits.
  - Error codes and messages are unchanged.
- **Upload policy discovery.** ([#156](https://github.com/Thiesi/ChitChat/issues/156), [#174](https://github.com/Thiesi/ChitChat/pull/174))
  - `GET /api/v1/session.php` gives signed-in members a top-level `attachments` block: the effective maximum file size, the allowed and previewable file types, and the room and direct-message upload quotas.
  - The size limit accounts for PHP's `upload_max_filesize` and `post_max_size` (less 64 KiB of headroom), and it's enforced exactly as advertised. `0` means no upload can fit with the current PHP limits.
- **Public installation metadata.** ([#149](https://github.com/Thiesi/ChitChat/issues/149), [#175](https://github.com/Thiesi/ChitChat/pull/175))
  - `session.php` now includes `application` (the effective installation name and the configured version) and `capabilities` (`schema_version: 1` plus native-authentication flags, currently `false`).
  - Both are available before sign-in and to guests.
- **Room list liveliness.** ([#153](https://github.com/Thiesi/ChitChat/issues/153), [#154](https://github.com/Thiesi/ChitChat/issues/154), [#177](https://github.com/Thiesi/ChitChat/pull/177))
  - Each joined room in `rooms/list.php` gains `active_count`: the number of other people present right now, guests included and each counted once.
  - It also gains `last_activity_at`: when the newest visible message was posted.
  - Both are `null` for rooms the viewer hasn't joined or can't currently read.

## Fixed

- **Oversized uploads get the right error.** ([#174](https://github.com/Thiesi/ChitChat/pull/174)) An upload larger than PHP's whole-request limit now returns `413 attachment_too_large` with `error.max_bytes`, instead of a misleading "field is missing" error. Every size rejection carries the limit.
- **Username searches treat `_` and `%` literally.** ([#152](https://github.com/Thiesi/ChitChat/issues/152), [#176](https://github.com/Thiesi/ChitChat/pull/176)) Mention suggestions, the direct-message recipient search, administration user and invitation searches, and the inspection search no longer treat these characters as wildcards. Searching `ann_` now finds only names that start with `ann_`.
- **Revision-review disclosure corrected.** ([#175](https://github.com/Thiesi/ChitChat/pull/175)) `privacy.message_revisions.participant_notification` now reports `true`, matching what the server does: a successful review notifies the room message's author, or both direct-message participants.

## Changed

- **Upload quotas are documented as attempts.** Each upload attempt counts towards the hourly quota, including rejected ones. The documentation previously said "successful" uploads. Behaviour is unchanged.

## Development and CI

- CI runners are pinned to Ubuntu 24.04, after `ubuntu-latest` moved to 26.04 ([#162](https://github.com/Thiesi/ChitChat/pull/162)).
- Local test scratch is bounded, with `composer clean-scratch` to remove it ([#161](https://github.com/Thiesi/ChitChat/pull/161)).

## What to evaluate

Operators staging this release should check that:

- the browser client works as before (sign-in, rooms, direct messages, attachments);
- `GET /api/v1/session.php` shows the installation's name and the expected `attachments.max_bytes` for a signed-in member;
- an upload above the advertised size is refused with "too large", both in a room and in a direct message.

## Database changes

`0040_room_activity_index.sql` adds the partial index `room_messages_latest_visible` on `room_messages (room_id, created_at DESC)` for messages that haven't been deleted. Building it briefly blocks writes to `room_messages`; on a large history that can take a moment. Run the migration during a quiet period. It changes no data.

## Upgrade from v3.2.1

1. Back up PostgreSQL and attachment storage together.
2. Deploy `v3.3.0` source.
3. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   ```

   `composer migrate` applies `0040_room_activity_index.sql`.
4. Verify `/health.php`, `/ready.php`, and that `GET /api/v1/session.php` reports `application.version` `3.3.0`.

Upgrading from before `v3.2.0` also applies that release's migration, `0039_guest_access.sql`; see its notes.

## Validation required for publication

The exact merged release commit must pass:

- locked Composer and npm dependency audits;
- PHP lint, JavaScript and stabilization-shell syntax checks, JavaScript unit tests, and PHPStan level 8 on PHP 8.2, 8.3 and 8.4;
- the complete PHPUnit suite against PostgreSQL 16 on PHP 8.2, 8.3 and 8.4;
- the full browser journey independently in Chromium, Firefox and WebKit;
- structural and keyboard accessibility checks in all three engines, and axe-core checks of both themes in Chromium;
- the dedicated first-class backup rehearsal;
- authenticated unbuffered SSE delivery through real Nginx and PHP-FPM.

Publication validation checks those named results on the exact 40-character merge commit before the annotated `v3.3.0` tag and stable GitHub release are created.

## Known limitations

Unchanged from `v3.2.1`. In addition, the native-authentication capabilities (`native_passkey_origins`, `native_auth_handoff`) report `false` until those features ship in a later release.
