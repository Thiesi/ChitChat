# ChitChat v2.0.0

`v2.0.0` is the fifth and **final** stable release of the clean ChitChat reconstruction. It adds Web Push notification delivery on top of the stable `v1.3.0` baseline, then closes out active development: ChitChat is now considered feature-complete.

## Project status: feature-complete

This is not an abandonment notice. ChitChat remains supported in the sense that it will resume work to fix a bug discovered in the shipped surface, or to evaluate a specific, concretely proposed new feature request. It will not resume open-ended roadmap work. See [`docs/roadmap.md`](../roadmap.md) for the full status of every feature this project ever considered — implemented, deliberately deferred, or postponed — and why.

This is an in-place application upgrade from `v1.3.0`. It applies the forward-only database migration `0022_web_push.sql`; after migration, do not run older ChitChat source against the upgraded database.

## Highlights

### Web Push notification delivery

- Optional browser push notifications for the same fixed, bounded set of events already recorded in the durable in-app notification timeline: `mentioned`, `revision_review`, `moderator_message_deleted`, `admin_password_reset`, and `system_policy_changed`.
- Disabled by default and inert (no subscribe control offered, dispatch command exits immediately) unless an operator configures a VAPID keypair — mirroring how passkeys stay inert without `WEBAUTHN_RP_ID`/`WEBAUTHN_ORIGIN`.
- Per-category mute for `mentioned`, the one social/conversational kind; the four security/audit kinds remain non-optional short of removing all subscriptions, matching how they already behave in-app.
- Per-account quiet hours (a local-time window, all three fields set together or not at all) suppress every category uniformly, mutable or not.
- Delivery runs through a new `bin/dispatch-web-push` periodic operator-scheduled sweep over undelivered notifications — not a request-time side effect, not a new queue or Redis service. Recommended cadence is every 30-60 seconds; ready-to-adapt `systemd` units are provided.
- Push payloads carry only the same sender-username/room-name/title text already considered safe for the in-app timeline, rendered through the same code path — never a raw message body.
- Introduces `minishlink/web-push` as this project's first production Composer dependency, for VAPID JWT signing and RFC 8291 payload encryption. See [ADR 0006](../architecture/0006-web-push.md) for the full design rationale.
- A "Push notifications" section on the privacy-notifications page: enable/disable push for the current device, mute `@mentions`, configure quiet hours, and manage a per-device subscription list with individual revocation.

## Also in this release

- **Design-token bug fixes.** A static audit found several stylesheets referencing CSS custom properties never defined anywhere, most visibly making the privileged step-up dialog — shown on any page, for any sensitive action — potentially render as a near-invisible white-on-white box. All affected declarations now reference the real token set.
- **Full documentation currency pass.** README, INSTALL, and every file under `docs/` were checked against actual source and brought current: previously undocumented endpoints, three ADRs still marked "implementation not started" for already-shipped features, an incomplete API-docs index, a new `docs/api/web-push.md`, and two independently-confirmed contradictions where documentation flatly claimed revision review never notifies participants (it does).
- **Reactions browser test coverage.** Message reactions previously had PHPUnit integration coverage only; every other post-`v1.2.0` feature already had a dedicated Playwright journey. Reactions now does too, covering aggregation, idempotent toggling, and realtime delivery on both room and direct messages.
- **License.** Replaced the existing BSD-3-Clause `LICENSE` with BSD-2-Clause.

## What to evaluate

Operators staging this release before a production upgrade should exercise:

- generating a VAPID keypair and confirming the subscribe control appears on the privacy-notifications page only once configured, and stays absent otherwise;
- subscribing a browser, receiving a push notification for a mention while the tab is closed, and confirming the notification body contains no message content;
- muting `mentioned` push and confirming it stops while a security/audit-category push (for example an administrator password reset) still arrives;
- configuring quiet hours and confirming push is suppressed inside the window and resumes outside it;
- revoking a device from the subscription list and confirming push stops for that device only;
- running `php bin/dispatch-web-push` on a schedule and confirming its JSON summary (`processed`/`sent`/`skipped_muted`/`skipped_quiet_hours`/`pruned_subscriptions`) matches expected activity;
- existing login, room, direct-message, attachment, search, moderation, reply, mention, reaction, inspection, export, retention, maintenance, and reverse-proxy SSE behavior remaining unaffected.

## Database changes

Upgrading from `v1.3.0` applies this forward-only migration:

- `0022_web_push.sql` — `push_subscriptions` and `notification_preferences` tables, three nullable quiet-hours columns on `users`, and a nullable `push_dispatched_at` column on `account_notifications`.

Back up PostgreSQL and attachment storage together before any deployment. Rolling back requires restoring a matching pre-upgrade database and attachment backup; there is no down-migration path.

## Upgrade from v1.3.0

1. Stop or drain application writes.
2. Create and verify a complete PostgreSQL-plus-attachment backup set.
3. Preserve `.env` and the existing attachment-storage path.
4. Deploy `v2.0.0` source.
5. Compare `.env` with `.env.example`. Retain existing values; optionally add `WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY`, and `WEB_PUSH_VAPID_SUBJECT` to enable Web Push.
6. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   composer maintenance:dry-run
   ```

7. If Web Push is enabled, schedule `bin/dispatch-web-push` — see [`docs/operations/web-push.md`](../operations/web-push.md).
8. Verify `/health.php`, `/ready.php`, login, room and direct-message history, attachments, SSE through the production reverse proxy, and, if enabled, a push subscription and delivery.

## Fresh installation

Follow `INSTALL.md`. Expose only `public/`, keep attachment and backup storage outside the web root, use HTTPS and secure cookies, provide enough PHP workers for open SSE requests, schedule maintenance and backups, and document the installation's inspection, retention, closure, MFA, notification, and restore policies before onboarding users.

## Security and privacy defaults

- Web Push is disabled by default and stays inert until an operator explicitly configures a VAPID keypair.
- A push payload never carries a raw message body — only the same sender/room/title text already rendered for the in-app timeline.
- `revision_review`, `moderator_message_deleted`, `admin_password_reset`, and `system_policy_changed` pushes cannot be individually muted; only removing every subscription stops them, matching their non-optional in-app behavior.
- Push subscriptions and notification preferences are cleared at the same account-tombstone point durable privacy notifications already are.
- The VAPID private key is deployment secret material, never sent to a browser or logged.
- Backup encryption, access control, off-host retention, restore authorization, maintenance scheduling, and release-specific manual assistive-technology validation remain operator responsibilities.

## Known limitations

- The supported deployment target remains one application server; horizontal scaling and Redis-backed event delivery are not implemented, and will not be — see the roadmap.
- PostgreSQL is the only supported database.
- Direct messages are not end-to-end encrypted, and will not be — see the roadmap.
- Optional external identity (OpenID Connect) integration was considered and postponed indefinitely rather than implemented — see the roadmap.
- Web Push has PHPUnit integration coverage but no dedicated browser end-to-end journey.
- Automated accessibility coverage is not a complete manual WCAG audit and does not prove NVDA or VoiceOver behavior. This remains a per-installation operator responsibility.
- No supported upgrade path exists from the incomplete legacy `v0.10.25` snapshot.

Detailed individual changes are listed in `CHANGELOG.md`. Because this is the final planned release, this list of known limitations is also final rather than a to-do list for a future version — see [Project status](#project-status-feature-complete).
