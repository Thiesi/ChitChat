# ChitChat v1.1.0

`v1.1.0` is the second stable release of the clean ChitChat reconstruction. It builds on the supported `v1.0.0` single-server baseline with direct-message controls and attachments, message mutation history, stronger administrative authentication and review boundaries, operational observability, personal-data export, WebKit validation, and accessibility hardening.

This is an in-place application upgrade from `v1.0.0`. It applies forward-only database migrations `0010` through `0013`; after migration, do not run older ChitChat source against the upgraded database.

## Highlights

### Direct-message and message controls

- Users can block and unblock another account from a direct-message conversation.
- A block in either direction prevents new text messages and file uploads while retained history remains readable.
- Direct messages support participant-only attachments using the existing opaque storage, MIME, size, checksum, and safe-preview policy.
- Authors can edit or delete their own room messages, direct messages, and attachment captions.
- Database-triggered revision ledgers preserve previous message and caption bodies until configured message retention removes the canonical record.
- Room moderator deletion remains separate from author deletion and continues to be audited.

### Administrative security and privacy

- Sensitive administrative actions require recent current-password step-up authentication in addition to the existing session, CSRF, role, target, reason, and audit checks.
- Step-up state is bound to the current account, session, and session version, expires after a configurable interval, and is cleared by authentication invalidation.
- Historical message-revision review is separately configurable, disabled by default, exact-message-ID only, reason-required, and audited without copying historical bodies into audit metadata.
- The Administrator system-status page reports aggregate database, storage, realtime, security-ledger, and maintenance health.
- An optional Prometheus endpoint remains unavailable until a sufficiently long bearer token is configured and exposes aggregate operational values only.

### Account portability

- Signed-in users can download a versioned JSON export of retained data associated with their account.
- Export generation requires recent password step-up, is rate-limited, reads a repeatable PostgreSQL snapshot, and creates an aggregate-only audit record.
- The export excludes credentials, session and step-up state, attachment bytes and storage keys, incoming block identities, other users' hidden revisions, and audit entries belonging only to another actor.

### Browser compatibility and accessibility

- The complete release journey now runs independently in Chromium, Firefox, and WebKit.
- Dependency-free browser checks cover document language and titles, unique IDs, visible main and heading structure, labelled controls, named interactive elements and dialogs, authentication-tab keyboard behavior, and visible focus indicators.
- Authentication tabs support arrow, Home, and End navigation with roving focus and explicit tab-panel relationships.
- Core user surfaces use stronger keyboard focus styling, a named room-creation dialog, and polite live connection-status semantics.

## Database changes

The upgrade applies these forward-only migrations:

- `0010_direct_message_blocks.sql` — directional direct-message blocks;
- `0011_direct_message_attachments.sql` — direct-message attachment metadata;
- `0012_message_mutations.sql` — room/direct-message revision ledgers and mutation support;
- `0013_operational_observability.sql` — SSE connection leases and maintenance-run records.

Back up PostgreSQL and attachment storage together before migration. Rolling back requires restoring a matching pre-upgrade database and attachment backup; there is no down-migration path.

## Upgrade from v1.0.0

1. Stop or drain application writes.
2. Back up PostgreSQL and the complete attachment-storage directory together.
3. Preserve `.env` and the existing attachment-storage path.
4. Deploy `v1.1.0` source.
5. Run:

   ```sh
   composer install --no-dev --classmap-authoritative
   composer migrate
   composer maintenance:dry-run
   ```

6. Review the new optional settings before enabling revision review or Prometheus metrics.
7. Verify `/health.php`, `/ready.php`, login, room and direct-message history, attachments, SSE through the production reverse proxy, account export, and the Administrator system-status page.

The automated release rehearsal installs the published `v1.0.0` archive, creates database and attachment backups, restores them under new names, applies the current migrations, and verifies retained accounts, room history, direct messages, and exact attachment bytes.

## Fresh installation

Follow `INSTALL.md`. A production installation should expose only `public/`, keep attachment storage outside the web root, use HTTPS and secure cookies, provide enough PHP workers for open SSE requests, schedule maintenance, and back up PostgreSQL and attachment storage together.

## Security and privacy defaults

- Direct messages are server-side PostgreSQL records and are **not end-to-end encrypted**.
- Administrative canonical DM inspection remains enabled for Super-Administrators by default, requires step-up plus a reason, and audits every successful page.
- Historical revision review is disabled by default and has an authorization policy independent from ordinary DM inspection and moderation roles.
- Room messages, direct messages, revisions, and audit entries are retained permanently until a Super-Administrator configures nonzero retention and maintenance runs.
- A block does not erase retained history and does not disclose through the public relationship contract whether the other participant blocked the current account.
- Attachment downloads always re-evaluate current participant or room authorization.
- Personal-data exports do not include attachment binaries or reveal another user's incoming block state or hidden revisions.

Operators must review and communicate the active inspection, revision, retention, export, and backup policies before onboarding users.

## Known limitations

- The supported deployment target remains one application server; horizontal scaling and Redis-backed event delivery are not implemented.
- PostgreSQL is the only supported database.
- Direct messages are not end-to-end encrypted.
- Revision review does not automatically notify affected participants; operators remain responsible for appropriate policy disclosure.
- Accessibility checks are regression smoke tests rather than a complete manual WCAG audit or visual-regression suite.
- Maintenance scheduling and alerting remain operator responsibilities.
- Account closure, multi-factor authentication, configurable per-limit throttles, and richer compliance/reporting workflows are not included.
- No supported upgrade path exists from the incomplete legacy `v0.10.25` snapshot.

Detailed individual changes are listed in `CHANGELOG.md`.
